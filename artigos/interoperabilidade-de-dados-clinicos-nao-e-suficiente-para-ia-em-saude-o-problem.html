Interoperabilidade de dados clínicos não é suficiente para IA em saúde: o problema é semântico

EA Por Equipe Editorial Médico AI

A interoperabilidade técnica entre sistemas de saúde resolve o problema errado. Trocar dados estruturados em HL7 FHIR entre um prontuário eletrônico e um modelo de IA não garante que o modelo entenda o que aqueles dados significam clinicamente. Esse é o argumento central que está ganhando força no debate sobre infraestrutura de IA em saúde, e ele tem implicações diretas para qualquer sistema que processe linguagem clínica em escala.

O problema não é o pipe, é o conteúdo

Quando um sistema exporta um campo chamado "diagnóstico principal" com o valor "J18.9", outro sistema recebe esse dado com perfeita fidelidade técnica. O FHIR foi cumprido. O HL7 está satisfeito. Mas se o modelo de IA que vai processar esse registro foi treinado em notas de triagem de um hospital universitário americano, e o dado veio de um ambulatório de atenção primária com padrão de registro completamente diferente, a equivalência formal entre os dois "J18.9" esconde uma diferença clínica real.

Isso não é bug. É estrutural.

O vocabulário controlado, seja CID-10, SNOMED CT ou LOINC, padroniza a representação, mas não padroniza o raciocínio clínico que gerou aquele código. Dois médicos que codificam "pneumonia não especificada" podem estar descrevendo apresentações, populações e contextos assistenciais completamente distintos. A IA que consome esses dados downstream não tem como inferir essa distinção a partir do código.

Por que isso importa agora

Esse problema existia antes da IA. Pesquisadores que faziam estudos de dados secundários já conviviam com ele há décadas. A diferença é que modelos de linguagem clínica, como os usados em sistemas de suporte à decisão, geração automática de sumários e análise preditiva, amplificam o ruído semântico em vez de filtrá-lo.

Um modelo treinado sem distinção entre populações, contextos de atenção e padrões de documentação vai aprender padrões espúrios. Vai correlacionar coisas que são artefatos de registro, não fenômenos clínicos. E vai fazê-lo com alta confiança estatística, que é exatamente o tipo de erro mais difícil de detectar na validação clínica.

O argumento que circula agora, especialmente em ambientes como o discutido no MedCity News, é que a solução não é mais padronização de formato. É construir o que alguns chamam de "representação compartilhada de significado clínico", ou seja, frameworks que explicitem o contexto por trás do dado, não apenas o dado em si.

O que seria essa "compreensão compartilhada"

Na prática, significa enriquecer os dados com metadados clínicos relevantes: qual foi o contexto de coleta, qual é o perfil da população, qual padrão de documentação prevalece naquele serviço, qual é a incerteza diagnóstica embutida naquele registro.

Algumas iniciativas já caminham nessa direção. O OMOP Common Data Model, amplamente usado em estudos de dados reais, tenta criar não apenas um formato comum, mas um modelo de representação com semântica mais estável. O HL7 FHIR R5 avançou em recursos de provenance, que permitem rastrear a origem e o contexto de cada elemento do registro. O próprio SNOMED CT, com sua estrutura hierárquica e relações polihierárquicas, foi concebido para capturar nuance clínica de forma que o CID-10 não consegue.

Mas adoção dessas camadas mais ricas ainda é fragmentada. A maioria dos sistemas que implementam FHIR usa apenas um subconjunto pequeno das suas capacidades, justamente as partes que facilitam a troca, não as que preservam o significado.

O que isso implica para quem desenvolve ou adota IA clínica

Qualquer ferramenta de IA que opere sobre dados de prontuário precisa ser avaliada não apenas por acurácia em benchmarks, mas por qual distribuição de dados ela foi treinada e como ela se comporta quando o contexto de origem difere do contexto de aplicação. Isso é especialmente relevante para modelos que chegam prontos de fora, treinados em populações e sistemas de saúde com padrões de documentação diferentes.

A pergunta que médicos e gestores deveriam fazer ao avaliar qualquer solução de IA clínica é direta: esse modelo foi validado em dados com o mesmo padrão de registro que o meu serviço usa? A resposta honesta, na maior parte dos casos, é não.

Isso não inviabiliza a IA em saúde. Mas exige que a camada de interpretação clínica continue sendo responsabilidade do médico, não do algoritmo.

Perguntas Frequentes

P: O FHIR não resolve o problema de interoperabilidade entre sistemas de saúde?
R: O FHIR resolve a interoperabilidade técnica, ou seja, a troca de dados em formato padronizado. Mas não garante equivalência semântica: dois registros com o mesmo código CID-10 podem representar contextos clínicos completamente distintos, o que compromete modelos de IA treinados nesses dados.

P: O que é o OMOP Common Data Model e por que ele é relevante para IA em saúde?
R: O OMOP CDM é um modelo de dados desenvolvido pela OHDSI que padroniza não apenas o formato, mas a representação semântica de dados clínicos de diferentes fontes. É amplamente usado em estudos de dados reais e permite que modelos de IA sejam treinados e validados em dados com estrutura e significado comparáveis entre instituições.

P: Como avaliar se um modelo de IA clínica é adequado para o meu serviço?
R: A pergunta central é se o modelo foi validado em dados com padrão de documentação, população e contexto assistencial semelhantes ao do seu serviço. Modelos validados apenas em dados de hospitais universitários americanos, por exemplo, podem ter desempenho imprevisível em atenção primária brasileira. Exija transparência sobre a distribuição dos dados de treinamento e validação antes de adotar qualquer solução.
